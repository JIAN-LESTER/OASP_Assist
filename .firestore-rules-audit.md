# Firestore access audit

This file records the access assumptions used to create the prototype rules.

## Collections and access model

- `users`: private profile/PII. Owners can read and update their own profile without changing UID, role, or administrative state. Staff and admins can read; admins can manage.
- `conversations/{conversationId}/messages/{messageId}`: owned by `userId` or legacy `userID`. The owner and staff/admin roles can read; the owner can create/update chat content.
- `escalations`: owned by `userId` or legacy `userID`. Owners can create/read; staff/admin roles can read and process.
- `notifications` and `fcm_tokens`: scoped to the authenticated recipient. Admin SDK notification functions bypass client rules.
- `colleges`, `programs`, and `affiliations`: public read because registration loads these reference lists before authentication; staff/admin management.
- `announcements`, `faqs`, `admissions`, `scholarships`, `placements`, and `information_bank`: authenticated read; staff/admin management.
- `faq_candidates`: authenticated creation; creator or staff/admin read; staff/admin management.
- `logs` and `message_logs`: authenticated creation for existing client logging; staff/admin read and management.
- Integration credentials, usage, scheduler, processing, and error collections: admin-only client access. Cloud Functions use the Admin SDK and bypass these rules.

## Query compatibility

The application queries managed content collections with `where`, `orderBy`, and `limit`, queries conversations/escalations by owner fields, and uses collection-group queries on `messages` for staff/admin reports. The path rules match those roles and ownership predicates.

## Adversarial review

- Public writes and non-reference reads: denied by the final catch-all rule. Only the three non-sensitive registration reference collections are publicly readable.
- Cross-user profile reads: denied to ordinary users; staff/admin access is required.
- Role/UID escalation: owner profile updates cannot change UID, role, administrative, creator, or verification fields.
- Conversation ownership hijacking: ownership fields are fixed after creation.
- Cross-user conversations/messages: denied unless staff/admin.
- Integration credential/token access: admin-only.
- Notification/token ownership: recipient UID must match the authenticated UID.
- Oversized core identity/content fields: bounded by the domain validators used on create and update.
- Orphaned message access: the parent conversation must exist and authorize the caller.
- Query mismatch: staff/admin collection and collection-group reports are allowed; ordinary users are restricted to owned data.

## Limitations requiring review

The project has legacy field variants and many optional generated-content fields. The validators preserve those schemas while bounding core text fields. Before a broad production launch, add emulator rule tests for representative documents from every collection and progressively tighten allowed-field lists.
